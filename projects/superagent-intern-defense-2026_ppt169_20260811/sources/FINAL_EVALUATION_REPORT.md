# 面向数字员工的上下文压缩、长期记忆与步骤/智能体 Skill 能力评测报告

**报告日期：** 2026-08-11  
**评测版本：** `cms-eval-v5`  
**评测对象：** SuperAgent 主 Agent、Planner、TaskGraph 执行链、上下文压缩、长期记忆和步骤/智能体 Skill 模块

## 摘要

数字员工需要持续处理长对话、跨会话保留稳定信息，并在不同任务中复用已经验证过的 Agent 调用方法。单纯扩大上下文窗口不能解决历史噪声、跨会话遗忘、重复规划和执行契约漂移，因此本项目把上下文压缩、长期记忆和步骤级 Skill 设计为三个相互独立但可共同注入主 Agent 的状态通道。

本轮评测保留 64 条跨模块结构化场景定义，并实际执行 3 条上下文压力工作流、64 条长期记忆专项案例、36 条步骤/智能体 Skill 专项案例和 17 条本地完整链路运行。长期记忆专项按照 4 类任务、2 类难度、每个单元 8 条构造，共 `4 × 2 × 8 = 64` 条；64 条均与预期模块行为一致。Skill 专项中 31/36 条与预期边界一致，另外 5 条集中暴露出数据范围字段规范化不一致的问题，作为真实研究发现保留。

## 1 方案采用原因与技术定位

### 1.1 为什么需要这套方案

第一，长对话会持续累积用户消息、工具结果和远端 Agent 回传。即使模型上下文尚未耗尽，过多历史内容也会增加 Token 成本，并使关键约束被中间噪声淹没。系统需要在压缩历史的同时保留未完成任务、当前 Plan、结构化结果和最近完整轮次。

第二，语言偏好、报告风格、文档格式、审批约束、稳定事实和项目范围具有跨会话复用价值，不应只存在于某一次对话摘要中。它们还会被重复确认、被新值替换或随时间失效，因此需要独立的生命周期、来源和用户范围。

第三，同一个 Agent 会反复执行相似步骤。若每次都重新探索工具、参数和输出契约，系统无法把成功经验转化为稳定能力。步骤级 Skill 用于沉淀“某个 Agent 完成某类步骤的可靠调用方法”，但不替换 Planner 对当前任务的完整规划。

### 1.2 采用的技术方案

1. **做法：对历史对话进行结构化压缩，不固定保留大量旧消息。**  
   **原因：** 长对话的主要问题不仅是超过上下文窗口，还包括历史噪声和 lost in the middle。把旧历史重写为结构化摘要，可以减少 Token，同时把请求、决策、错误、文件和待办组织成更适合恢复的形式。

2. **做法：压缩后最多保留最近两个完整对话轮次。**  
   **原因：** 最近轮次通常包含用户刚刚给出的修正和承接关系，保留完整内容比再次摘要更可靠；限制为两轮则避免“保留最近 N 轮”重新占满上下文。

3. **做法：执行中的 Plan / TaskGraph 不进入摘要，任务结束后才作为普通历史处理。**  
   **原因：** 未完成 Plan 是当前执行状态，不是一般聊天内容。如果在子 Agent 仍在运行时被压缩，主 Agent 可能丢失步骤依赖、完成状态和下一步；已完成 Plan 则没有继续占用独立恢复预算的必要。

4. **做法：System Prompt 不参与压缩，每轮按最新工具、权限和配置重新构造。**  
   **原因：** System Prompt 属于运行环境而不是会话历史。重新构造可以让对话中途发生的工具、权限或 Agent 配置变化立即生效，也避免摘要模型误改系统约束。

5. **做法：LLM 摘要失败时使用确定性兜底，并强制压缩后 Token 小于压缩前。**  
   **原因：** 模型可能返回非法结构、调用工具或生成比原文更长的摘要。确定性兜底保证流程可继续，Token 单调下降门禁保证“压缩”确实释放上下文，而不是只生成另一段长文本。

6. **做法：长期记忆采用固定办公标签，不由模型自由创建无限标签，也不在当前阶段依赖 Embedding。**  
   **原因：** 语言、报告风格、文档格式、审批、隐私、身份和周期任务等办公信息维度有限。固定标签便于全量召回、审计、冲突判断和权限控制，也能降低小规模原型引入向量模型与向量库的成本。

7. **做法：长期记忆在完整用户回合结束后由后台任务提取。**  
   **原因：** 提取需要额外模型调用，把它移出用户响应关键路径可以降低可感知延迟；只处理已完成回合，也避免把正在生成或被取消的内容写成长期事实。

8. **做法：每条长期记忆保存来源消息、来源会话、用户/项目范围和生命周期状态。**  
   **原因：** 长期记忆会影响后续任务，必须能够回答“这条信息从哪一轮对话得到”。用户和项目范围防止跨用户或跨项目串用，来源记录支持人工查证、重新强化和删除。

9. **做法：重复内容强化原记录，冲突内容保留旧版本并激活新版本，旧记忆按时间衰减。**  
   **原因：** 重复确认说明记忆更稳定，不应制造重复项；冲突通常表示用户修改了偏好或事实，不能让新旧值同时生效；衰减用于降低长期未确认内容的召回权重，但不删除审计来源。

10. **做法：长期记忆只注入主 Agent，远端 Agent 只接收当前 Plan 已选择的必要信息。**  
    **原因：** 主 Agent 负责理解用户偏好和生成任务边界，远端 Agent 只需执行具体步骤。直接向远端发送长期记忆原文会扩大隐私面，并把无关信息带入工具执行。

11. **做法：Skill 采用 Step/Agent 粒度，不再沉淀整条 Workflow Skill。**  
    **原因：** 完整工作流会随任务实体、步骤数量和 Planner 结果变化，复用风险高；某个 Agent 完成某类步骤的工具链和输入输出契约更稳定，也更容易与当前 Plan 做局部组合。

12. **做法：先由 LLM 反思判断是否属于常规可复用流程，再检查至少两次独立成功证据。**  
    **原因：** 仅凭 Agent 名称、工具链和 Schema 相同，无法排除一次性任务或偶然成功。反思负责语义层的“值不值得沉淀”，双证据负责执行层的“是否已经稳定”。

13. **做法：Skill 晋升和复用都校验 Agent、工具、输入输出、Schema、用户、数据范围和副作用等级。**  
    **原因：** 相似描述不代表契约兼容。结构或身份变化时继续复用可能向错误对象读取、写入或发送数据，因此不兼容时必须拒绝，而不是依赖 Agent 自行猜测。

14. **做法：命中 Skill 后只在对应 Plan 步骤附加引用与执行指导，不跳过 Planner。**  
    **原因：** Skill 解决的是“这个步骤怎么稳定执行”，Planner 解决的是“当前任务需要哪些步骤以及它们如何依赖”。两者职责不同，完全跳过规划会丢失当前用户实体、任务边界和跨步骤关系。

### 1.3 技术特点与边界

上述 14 项设计共同解决三类核心问题：长对话 Token 增长和任务状态丢失、跨会话偏好与事实遗忘、重复 Agent 步骤无法稳定复用。方案的重点不是增加一张统一“记忆表”，而是让会话历史、长期用户信息和程序性执行经验分别拥有适合自己的存储、更新、召回和失效规则。

本方案的先进性主要体现在系统组合与治理，而不是宣称某个单项算法达到行业最优：

- 将会话压缩、跨会话长期记忆和跨任务程序性 Skill 分成三个生命周期，避免把摘要、用户事实和执行方法混为同一类记录。
- 在压缩后重新组装运行状态，而不是只保留一段摘要；这使未完成 Plan、TaskGraph 和 Artifact 可以继续参与执行。
- 长期记忆保留原始来源轮次，并同时处理重复强化、冲突替换、用户/项目隔离和时间衰减，适合对审计要求高的办公场景。
- Skill 从成功步骤证据中产生，采用“LLM 反思 + 两次独立证据 + 契约门禁”晋升，并在 Plan 中做增量绑定，而不是跳过规划阶段。

当前方案属于“参考前沿机制形成的可验证工程原型”，不能表述为已达到通用记忆或 Skill 评测的 SOTA。长期记忆尚未实现语义、关键词和实体多信号融合，也没有时间知识图谱；Skill 的 LLM 反思尚缺少人工标注的大规模语义准确率评测；上下文压缩尚未覆盖完整 Hook 和全部工具结果的时间衰减式 microcompact。

## 2 研究设计

### 2.1 研究问题

本评测分别回答三个问题：

1. 压缩后，主 Agent 是否仍能恢复当前任务、关键事实、Plan / TaskGraph 和结构化 Artifact，并继续完成后续步骤。
2. 长期记忆是否能稳定召回标签化信息，正确处理重复、冲突、来源、用户/项目隔离、置信度、过期和时间衰减。
3. Skill 是否能区分“结构兼容可复用”和“看似相似但契约或风险不兼容”，并把指导绑定到正确的 Agent 步骤。

### 2.2 证据层次

结构化场景定义用于描述办公领域、难度和预期边界；只有真正调用项目模块或完整执行链并产生断言的案例才计入实际结果。长期记忆本轮新增 64 条真实模块执行，不再使用原先 9 条原子检查代表更大的场景集。Skill 使用 36 条真实治理模块执行；上下文压缩使用三档压力配置和压缩后的接续工作流；17 条端到端运行用于验证模块之间的连接关系。

本轮不把确定性模块测试等同于在线大模型语义能力。长期记忆 64 条验证的是 MemoryStore、标签召回器和治理状态机；Skill 36 条使用确定性 reflection 替身隔离晋升与匹配逻辑。在线 LLM 提取和反思仍需单独评测。

### 2.3 案例构造

长期记忆专项由四类任务组成：

- 偏好记忆：语言、报告风格、文档格式、回复风格和沟通渠道。
- 办公约束：审批、隐私和日程边界。
- 稳定事实：姓名、角色、组织和周期任务。
- 项目范围：项目决策、项目时间约束和项目周期任务。

每类任务包含两档难度，每档 8 条。常规样本验证标签召回和来源记录；对抗样本依次验证重复强化、冲突替换、跨用户隔离、范围隔离、陈旧衰减、低置信度拒绝、过期拒绝和有效版本唯一性。因此长期记忆总样本数为 `4 类任务 × 2 类难度 × 8 条 = 64 条`。

Skill 专项从项目已有远端 Agent 契约抽取六类步骤族：员工信息查询、薪资结构查询、制度条款检索、正式报告生成、办公日程整理和邮件发送。每个步骤族执行首次证据建档、两次独立证据晋升、实体变化复用、契约与 Schema 漂移拒绝、用户/数据范围隔离、反思或业务身份门禁六个判定，共 36 条。

### 2.4 指标定义

上下文压缩使用 Token 降幅、关键事实召回、最近完整轮次、压缩后工作流接续、Artifact 完整性和禁止副作用次数。

长期记忆使用标签召回 Precision、Recall 和 F1，以及重复合并、冲突更新、来源覆盖、用户/范围隔离、时间衰减、低置信度拒绝、过期拒绝和有效版本唯一性。Precision、Recall 和 F1 根据全部 64 条案例中实际应召回与应拒绝的记录集合统一计算。

Skill 使用证据建档、晋升、结构复用、不兼容拒绝、来源审计和边界门禁六类指标。报告不以 Skill 记录总数或单一总通过率代替能力边界分析。

## 3 研究成果

### 3.1 上下文压缩：Token 控制与任务接续

三档上下文压力均完成真实压缩后的恢复验证。8K 配置触发 4 代压缩，Token 从 4,426 降至 3,460，下降 21.8%；16K 配置触发 4 代压缩，从 6,939 降至 6,262，下降 9.8%；32K 配置触发 1 代压缩，从 11,905 降至 6,137，下降 48.5%。三档均保留最近两个完整轮次，关键事实召回为 4/4。

![图 3-1 不同上下文规模下的 Token 变化](showcase_figure_2_context_tokens.png)

压缩后重新执行 3 条年假政策分析工作流，共恢复 9 个步骤和 9 个结构化 Artifact，报告事实命中为 9/9，禁止的外部副作用为 0 次。这说明压缩结果能够作为主 Agent 的下一轮恢复上下文继续工作，而不仅是生成一份归档 Markdown。

![图 3-2 压缩后的任务接续能力](showcase_figure_4_context_continuity.png)

### 3.2 长期记忆：64 条实际模块评测

长期记忆专项实际执行 64 条，四类任务各 16 条，其中常规与对抗难度各 8 条。偏好记忆、办公约束、稳定事实和项目范围四类均为 16/16 与预期一致，总体为 64/64。

聚合召回统计为 `TP=44、FP=0、FN=0`，因此 Precision、Recall 和 F1 均为 1.0。来源消息和来源会话覆盖 40/40 条需要来源证明的正向记录；重复合并为 4/4，冲突更新为 4/4，跨用户与范围隔离为 8/8，陈旧记忆衰减为 4/4，低置信度拒绝为 4/4，过期拒绝为 4/4，有效版本唯一性为 4/4。

时间衰减的独立曲线使用距上次强化 0、30、90 和 180 天的样本，召回权重依次为 0.855、0.679、0.428 和 0.214。衰减只降低召回权重，不删除来源事实，因此仍可通过来源会话完成审计和重新强化。

![图 3-3 长期记忆的更新与时间衰减](showcase_figure_5_memory_decay_update.png)

这些结果证明固定标签方案在受控输入下的存储、召回和治理状态机行为稳定，但不能直接解释为 LLM 能从任意自然语言中 100% 正确提取记忆。后者需要引入人工标注的真实对话，并分别测量“是否应该记”“标签是否正确”“值是否正确”和“来源是否正确”。

### 3.3 步骤/智能体 Skill：36 条能力边界评测

专项基准共执行 36 条，覆盖六类 Agent 步骤族。首次证据建档、独立证据晋升、契约与 Schema 漂移拒绝、用户/数据范围隔离、反思或业务身份门禁均为 6/6 与预期一致。

实体变化复用是本轮最重要的边界发现：邮件步骤按高风险副作用策略预期不自动复用，1/1 正确保持阻断；其余 5 个低风险步骤本应在实体变化而结构不变时命中，但实际均未命中。代码检查表明，计划侧数据范围经过规范化，而已保存 Skill 卡片仍保留原始点号格式，最终导致集合比较失败。

![图 3-4 Skill 能力判定结果](skill_capability_figure_2_results.png)

Skill 记录数、证据数和复用次数只用于运行审计，不作为核心能力指标。真正需要衡量的是可复用流程能否命中，以及契约、身份或风险不兼容时能否拒绝。

### 3.4 端到端运行证据

独立于模块专项评测，项目已有 17 条本地完整链路运行：3 条上下文压力工作流、3 条失败隔离工作流、8 条审批/副作用策略工作流和 3 条 Skill 生命周期工作流。它们验证主 Agent、Planner、TaskGraph、远端 Agent、Artifact、Checkpoint、Memory 和 Agent Skill 之间的连接关系。

17 条端到端运行不能替代 64 条长期记忆和 36 条 Skill 边界基准。前者证明链路可以运行，后者证明模块在不同输入关系和风险边界下如何判定；两类证据分开统计。

## 4 结论与改进建议

上下文压缩已经显示出直接运行价值：Token 下降后，任务、步骤、Artifact 和报告事实仍能恢复。下一阶段应测试更长时间跨度、不同类型远端 Agent 回传，以及压缩失败重试和重启恢复。

长期记忆固定标签方案在 64 条确定性模块案例上完成了召回、更新、来源、隔离和衰减验证。下一阶段不应继续复制同类确定性样本，而应评测真实 LLM extraction：至少构造显式偏好、隐式倾向、短期信息、冲突修正、恶意注入和不应记忆内容，并由人工给出标签与来源金标准。

Skill 评测已从记录数量转为 36 条能力边界案例。当前首要修复项是统一计划侧与 Skill 卡片侧的数据范围规范化；修复后重跑 5 条低风险实体变化复用案例，再增加输入绑定变化和向后兼容 Schema 的样本。

本项目的主要价值是把三种状态放入同一数字员工执行闭环，并保留来源与治理边界；当前主要差距是缺少多信号语义记忆、时间知识图谱和真实 LLM 反思/提取基准。因此应定位为“机制完整、可复核、已形成专项评测的工程原型”，而不是泛化能力已经充分验证的成熟产品。
