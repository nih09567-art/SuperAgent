# 数字员工答辩问答速查：主 Agent 路由与权限治理

适用材料：`数字员工-刘建杰.pptx`，共 8 页。本文答案按当前 SuperAgent 原型、33 条意图评测及 2026-08-12 核心回归结果整理。

## 一、先背这段 30 秒总述

我的课题解决两个问题：第一，用户给出长指令或复合任务时，主 Agent 怎样准确理解任务并选择合适的专业 Agent；第二，即使模型理解或选择出错，系统怎样阻止越权操作。我的方案是先把自然语言转换成结构化 `TaskProfile`，再依据 `AgentCard` 构造合法候选集合并进行可解释评分；执行阶段用 S-ABAC 在路由、派发、工具和结果四个节点重复鉴权。当前原型的重点不是让模型拥有更大权限，而是把模型的建议限制在确定性的契约和权限边界内，并让每次选择、拒绝和审批都可追踪。

## 二、回答问题的固定结构

现场回答尽量按五句话组织：

1. 先说结论。
2. 再说解决的具体问题。
3. 再说实现机制或代码对象。
4. 再给评测或测试证据。
5. 最后主动说明原型边界和下一步。

不确定时可以说：

> 这个问题需要区分设计目标和当前原型。设计上我们希望做到……；当前已经实现并验证的是……；还没有完成的是……。我不把原型测试结果外推为生产结论。

## 三、最高频问题

### 1. 你的课题到底解决了什么问题？

核心是让数字员工系统同时做到“选得对”和“即使选错也不能越权”。前一部分通过 `TaskProfile + AgentCard + RoutingDecision` 解决任务理解和可解释路由；后一部分通过 S-ABAC、四道 PEP、审批、Artifact Guard 和审计解决执行安全。两部分不是并列功能，而是一条闭环：路由决定谁适合做，权限决定谁被允许做。

### 2. 为什么要有主 Agent，直接让多个 Agent 自由协作不行吗？

自由协作适合开放讨论，但企业任务还要处理责任主体、数据范围、停止条件和审计。主 Agent 作为唯一跨部门入口，统一保存用户目标、拆分任务、筛选候选并汇总结果；专业 Agent 只接收边界明确的子任务。这样可以避免 Agent 之间自由转交时逐步扩大上下文和授权范围。

### 3. `TaskProfile` 与普通意图分类有什么区别？

普通分类通常只输出一个标签，例如“工资查询”。`TaskProfile` 还包含主意图、子意图、实体、动作、数据范围、风险、不可逆标记、缺失字段、否定、条件和依赖，所以它是一个可供 Router、Planner 和权限引擎共同校验的任务契约。它的价值不是标签更多，而是把自然语言变成可执行、可验证、可审计的结构。

### 4. 为什么采用规则和 LLM 混合识别？

两者分工不同。规则适合动作词、格式化实体、否定范围和高确定性业务边界，稳定、低时延且可离线；LLM 适合同义表达、隐含意图和复杂条件，但存在漂移。设计上先让两路产生候选，再经过意图目录、冲突检查和 Pydantic Schema 约束；语义服务异常时可以退回规则基线。需要说明的是，PPT 第 5 页展示的 33 条数据是可离线复现的规则模式结果，不是混合模式的线上效果。

### 5. 否定和条件意图怎么处理？

否定动作会保留在 `intent_nodes` 中用于解释和审计，但不会进入可执行子任务，例如“生成报告但不要发送”中的“发送”不能被执行。条件动作会转换成明确的执行策略和依赖关系，例如“审批通过后再发送”。这样可以避免模型只识别到动作词，却丢失动作的否定范围或前置条件。

### 6. `AgentCard` 是什么？

它是专业 Agent 的能力与安全说明书，包含支持的意图、能力、动作、数据范围、场景标签、风险上限、所需授权、工具范围、输入输出 Schema、版本和在线状态。Router 不根据 Agent 名称猜能力，而是根据这张卡进行筛选和评分。进入规划的 Agent 还要求具备受信的 `AgentContract`，防止 Planner 虚构 Agent 或输入输出。

### 7. 为什么必须先硬过滤再评分？

因为权限不是可以被高语义分抵消的软因素。当前实现中，无权和离线 Agent 会直接进入排除列表；对非复合任务，动作不支持或风险超过上限也会被排除，只保留 `reason_code`，不参加 Top-K 评分。复合任务目前侧重检查子任务能力覆盖，子任务级动作、风险和范围仍需由后续 Planner 校验与 PEP 拦截；下一步应把这些约束也前移成逐子任务硬过滤。

### 8. 路由评分公式为什么这样分配权重？

当前权重是工程先验，不是训练得到的最优参数：意图 0.35、能力 0.25 是主要因素，场景 0.15，数据范围和历史各 0.10，可用性 0.05。这样设计是为了让业务语义和真实能力占主导，同时保留范围、历史和状态的区分度。当前原型中的 history 为 0.5、availability 为 1.0 的固定基线，还没有接入真实线上成功率和健康度；生产化需要用历史数据、消融实验和阈值校准重新学习或验证权重。

### 9. `ROUTE / CLARIFY / REJECT` 分别是什么？

含义分别是：存在明确合法候选则派发；关键信息缺失则先澄清；没有合法候选或复合任务覆盖不完整则拒绝。当前代码中的成功终态实际命名为 `DISPATCH`，PPT 的 `ROUTE` 是面向汇报的概念名称。澄清必须能提出具体问题，例如“请提供收件人”，不能因为分数一般就无目的追问。

### 10. 没有合适 Agent 时为什么不能交给通用 Agent？

因为通用 Agent 的能力和权限半径通常更大，自动降级会把“没有合法能力”变成“扩大权限后尝试”，违背最小权限原则。系统返回 `REJECT` 或 `NO_CAPABLE_AGENT`，并保留是能力不足、权限不足还是复合任务覆盖不完整。后续应由管理员补充合法能力或由用户缩小任务范围，而不是静默越权。

### 11. 复合任务如何路由？只选一个 Agent 吗？

复合任务先拆成带依赖的子任务，再检查合法候选集合能否覆盖全部子任务。单个候选的分数不代表整条任务可执行；只有覆盖完整才进入 Planner，由 Planner 生成多 Agent 计划并继续做契约和 DAG 校验。覆盖不完整时直接拒绝，并指出缺失的是能力还是权限。

### 12. 数据范围到底是硬约束还是评分项？

需要区分“字段贯穿链路”和“通用策略已经硬执行”。当前 `data_scope` 会进入 TaskProfile、RouteScore、TaskStep 和安全上下文，但 Router 中它仍是评分项；现有 PolicyEngine 也还没有实现通用的“请求范围与资源允许范围”集合比较。当前真正硬执行的数据边界主要是 Agent 可见性、角色/grant、动作、敏感级别、Artifact 所有权和受信共享名单。因此不能宣称任意数据范围都已由 S-ABAC 完整拦截；下一步要在 Router 和 PolicyEngine 中补上统一、可测试的 scope containment 规则。

## 四、评测数据追问

### 13. 33 条测试用例是怎么来的？够不够？

它是第一期结构化任务画像回归集，覆盖单意图、跨域复合任务、隐式依赖、否定、条件、缺失字段、同义表达和关键词边界等场景，并分为 regression、challenge 和 semantic 层。它适合验证机制和防止代码回退，但样本量不足以代表真实用户分布，也不能给出统计显著的生产准确率。下一步需要盲测集、真实脱敏请求、对抗样本和持续回归，并把训练/调参数据与最终测试集分开。

### 14. 93.94% 是怎样算的？

这是主意图准确率，33 条用例中 31 条主意图与标注完全一致，即 `31/33 = 93.94%`。它只说明主标签，不代表整条结构化任务全部正确，所以必须同时看实体、依赖、澄清和严格整例指标。

### 15. 子意图 Recall 98.48% 是什么意思？

每条用例分别计算“标注子意图中有多少被召回”，再对用例取平均。它反映复合任务是否漏掉动作，但不能单独说明顺序、实体和依赖都正确。因此高 Recall 与严格整例较低并不矛盾。

### 16. 实体字段 96.46% 是怎样算的？

每条用例按标注实体字段逐项比较实际值，得到该用例的字段匹配比例，再对用例平均。它比只判断“有没有识别到人名”更严格，因为员工、时间、收件人等字段和值都要对应。当前短板主要出现在隐式员工上下文和少量复合表达。

### 17. 依赖完整 92.31% 是什么口径？

对 26 条带依赖标注的用例，实际依赖边集合必须与期望集合完全一致；24 条通过，因此为 `24/26 = 92.31%`。这里不是只检查子任务都出现，还要检查“谁依赖谁”的方向和完整性。

### 18. 澄清触发 75% 为什么只有 8 条样本？

只有 8 条用例显式标注了是否需要澄清，其中 6 条判断正确，所以是 `6/8 = 75%`。这个指标样本很少，只能作为缺陷定位信号，不能当成稳定泛化结论。当前两个失败主要与否定表达下的 missing fields 和澄清判断有关。

### 19. 为什么严格整例只有 60.61%，是不是效果很差？

严格整例要求一条用例的所有已标注项同时正确，包括主意图、子意图、实体、动作、依赖、缺失字段、风险、置信度区间和澄清等，任何一项不符整例都失败。当前为 `20/33 = 60.61%`；13 个失败中不少是置信度区间、缺失字段或依赖不完全，而主意图只错了 2 条。这个指标揭示的是端到端结构一致性仍需优化，我不会用几个超过 90% 的单项指标掩盖这一短板。

### 20. 90% 目标线从哪里来？

它是课题对关键字段设置的工程验收线，不是行业统一标准，也不是与其他框架横向测试得到的基准。它用于快速判断主意图、实体、依赖等关键模块是否达到第一阶段可用水平。严格整例和澄清还未达到同样水平，因此不能说整个意图识别已经达到 90%。

### 21. 你们与 OpenAI Agents SDK、LangGraph 的对比公平吗？

这张表比较的是公开机制与职责边界，不是用同一数据集做准确率排名。OpenAI Agents SDK 提供 manager、handoff、guardrail 和 tracing 等原语；LangGraph 强项是显式图、持久化和恢复；企业数据范围、岗位授权和任务级审批仍需要应用层建模。SuperAgent 的取舍是吸收 manager 和显式图思想，再补充自身的业务契约和权限闭环，不能表述为全面优于这些框架。

## 五、S-ABAC 与四道 PEP

### 22. S-ABAC 是什么？这是行业标准吗？

S-ABAC 是本项目对 ABAC 的场景化工程扩展，S 强调 Scenario。它仍按 Subject、Object、Scenario、Action 四组输入进行确定性授权：谁在操作、操作什么、为何及在什么环境操作、具体做什么。S-ABAC 不是新的国际标准，基础思想来自 ABAC 和零信任；创新点在于把数字员工的任务目的、Agent/Tool/Artifact 和审批状态统一纳入原型实现。

### 23. 为什么不用 RBAC 就够了？

RBAC 很适合表达稳定岗位，是 Subject 属性的重要来源，但仅凭“某人是 HR”还不能回答他能否在当前任务中读取某位员工的敏感数据、调用什么工具、是否外发以及是否需要审批。S-ABAC 不是替代 RBAC，而是在角色基础上继续结合对象敏感度、任务目的、数据范围、环境和动作。生产系统通常会是 IAM/RBAC 提供身份与基础角色，策略引擎完成细粒度判定。

### 24. LLM 会不会直接决定权限？

不会。LLM 最多辅助判断任务场景与目标资源是否匹配，最终结果由 `PolicyEngine` 的确定性规则输出。场景明确不匹配时拒绝；场景不确定且资源高敏或动作不可逆时进入 `REVIEW_REQUIRED`；普通规则、角色、grant、敏感级别和操作模式仍要逐项通过。

### 25. `ALLOW / REVIEW_REQUIRED / DENY` 为什么要三态？

二态模型无法区分“明确禁止”和“原则上允许但需人工确认”。`ALLOW` 直接执行，`REVIEW_REQUIRED` 暂停并生成绑定当前上下文的审批，`DENY` 直接失败。人工审批只能消费一个原本为 `REVIEW_REQUIRED` 的决定，不能把 `DENY` 改成允许。

### 26. 审批如何防止一张票到处使用？

审批签名绑定完整的 Subject、Object、Scenario 和 Action，包含用户属性、资源属性、任务场景、操作模式和调用参数，并按 `task_id` 查找。批准后会原子地标记为 `consumed`，同一新请求不能再次消费；同一步骤跨多个门禁时，只在本次内存执行上下文内复用。原型目前主要依赖进程内锁和文件原子替换，跨进程强一致性仍应迁移到带事务或租约的数据库。

### 27. 为什么需要四道 PEP，一次鉴权不够吗？

四次检查的对象和时刻不同。路由前检查候选可见性，派发前检查实际 Agent 与当前步骤，工具前检查真实工具和参数，结果前检查 Artifact 的所有者、敏感度和受信共享关系。这样可以防止计划变化、参数变化、工具绕过和越权读取，也符合“每次访问都重新验证”的零信任思想。通用数据范围比较仍是下一步补强项，不能用四道 PEP 的数量替代每道策略的完整性。

### 28. 四道 PEP 分别在哪里起作用？

- 路由 PEP：无权 Agent 不进入合法候选集合。
- 派发 PEP：执行前重新检查目标 Agent、动作、场景、角色/grant、敏感级别和风险条件。
- 工具 PEP：逐次检查工具归属、调用参数、操作模式和审批状态；远程工具也要经过 Tool Gate。
- 结果 Guard：通过 `ArtifactRef -> Resolver -> ArtifactGuard` 的统一读取路径检查所有者、受信共享名单、敏感级别和策略；存储层同时校验 checksum。

### 29. 什么叫 Fail Closed？

就是关键属性缺失、主体未知、资源未知、策略异常、Artifact 缺失或校验失败时，默认不执行、不返回敏感结果。只有策略引擎明确判定为 `REVIEW_REQUIRED` 的业务情形才允许进入人工审批；技术校验失败和明确 `DENY` 应直接 `DENY/STOP`。因此不能把 Fail Closed 概括成“出错后都可以人工放行”。

### 30. 如果关闭 S-ABAC，系统是不是仍然安全？

不能这样宣称。当前原型关闭总开关后，Agent/Tool 的普通 S-ABAC enforcement 会旁路；但 Artifact Guard 仍对跨用户读取失败关闭，并拒绝 confidential/restricted 数据。演示配置会显式启用 S-ABAC，生产环境还需要配置锁定、启动检查和不可由普通用户修改的策略部署。

### 31. Artifact Guard 具体保护什么？

每个 Artifact 带有 owner、producer、sensitivity、checksum 和 `derived_from` 等元数据，步骤间只传 `ArtifactRef`。读取时先做所有权检查，跨用户访问必须来自受信服务端的 `allowed_reader_ids`，再进入策略判断；payload 存储和 checkpoint 分离，checkpoint 只保存引用、校验和、逻辑名和敏感度。这样减少敏感正文进入通用状态和审计日志的机会。

### 32. SHA-256 校验和能防篡改吗？

只能严谨地说它能发现意外损坏和“只改 payload、不改 checksum”的简单修改，不能说实现了密码学防篡改。能同时修改文件和 checksum 的攻击者仍可绕过。生产化需要受保护的密钥、HMAC 或数字签名，以及数据库/对象存储的访问控制和静态加密。

### 33. 审计日志是否不可篡改？

当前是按任务分区的追加式 JSONL 治理事件和独立 Artifact 访问日志，重点是可追踪且不记录 payload 正文，不是不可篡改账本。生产环境应写入集中式、访问受控、带保留策略和完整性保护的审计平台。这里应说“已实现审计留痕”，不要说“已实现防篡改审计”。

### 34. Prompt 注入能绕过权限吗？

Prompt 注入可能影响模型对意图或计划的建议，但不能直接改变确定性 PolicyEngine、AgentCard、工具归属和 Artifact 所有权检查，所以硬门禁能限制它的执行后果。不过原型不能宣称彻底解决 Prompt 注入；生产化还需要可信工具网关、输入输出检测、最小权限凭证、隔离执行和针对间接注入的专项测试。

### 35. 如果 Agent 绕开主 Agent 直接调用工具怎么办？

系统内已接入的本地和远程工具调用都应经过统一 enforcement/Remote Tool Gate，不能只依赖主 Agent 的一次判断。但如果开发者把新工具接到门禁之外，仍会形成旁路风险。生产接入规范必须要求所有工具通过受信网关注册，并用底层凭证权限保证即使应用代码出错也不能扩大访问。

## 六、创新、贡献与落地边界

### 36. 你的创新点是什么？

我不把它包装成新的基础模型算法。主要创新是工程体系：第一，把意图分类扩展为带动作、范围、风险、否定和依赖的 `TaskProfile`；第二，在打分前构造授权且有能力的合法候选集合；第三，把 S-ABAC 的任务场景授权落实到路由、派发、工具和结果四个执行点；第四，让路由、排除、审批和结果访问都产生结构化证据。价值在于把“模型觉得可以”变成“系统验证后才可以”。

### 37. 你个人做了什么？

我的主要职责是主 Agent 决策与路由、S-ABAC 权限治理和系统集成。具体包括 `TaskProfile`、`AgentCard`、`RoutingDecision` 的契约与链路，权限感知候选过滤和可解释评分，三态策略、审批、四道 PEP、Artifact Guard，以及相关评测、回归和页面联调。回答时只讲自己确实完成或主导的部分；团队共同完成的内容要明确说“共同联调”，不要全部归为个人成果。

### 38. 项目带来了什么业务价值？

目前能量化的是技术机制，不是生产 ROI：主意图 93.94%、实体字段 96.46%、依赖完整 92.31%，以及本次选取的 115 项路由和权限核心回归全部通过。业务上的预期价值是减少误派发、提前澄清缺失信息、阻止越权并缩短问题追溯时间，但还没有真实生产用户、工时节省或风险损失数据，所以不能虚构业务收益。

### 39. 115 项通过是否说明系统已经安全？

不说明。115 项是我在 2026-08-12 针对意图识别、复合路由、审批、Artifact Guard、远程工具门禁和调度终态重新运行的专项回归，结果是 115/115；它证明这些已覆盖合同按预期工作，不代表全系统、所有配置或真实攻击面都验证完毕。安全结论还需要威胁建模、渗透测试、依赖治理、密钥管理和生产环境评估。

### 40. 当前最大的不足是什么？

任务理解侧是严格整例和澄清触发不足，尤其是隐式依赖、同义改写、字段完整性和少量关键词边界；路由侧的历史与可用性还没有真实在线数据，复合任务的动作/风险硬过滤和通用数据范围策略也不完整；治理侧仍缺正式身份认证、生产级密钥管理、静态加密、跨进程事务审批和集中式防篡改审计。这些是明确的工程化路线，不回避原型边界。

### 41. 下一步如何生产化？

先把身份和角色接入企业 IAM，将策略迁移到 OPA、Cedar 或等价的集中 PDP；所有 Agent、Tool、Artifact 都从受信注册中心获取版本化属性。随后把审批和回执迁移到事务数据库，接入 KMS 与 AES-GCM、集中审计、实时健康度和历史成功率，再用真实脱敏任务做盲测、压力测试、红队测试和灰度发布。最后才讨论业务 SLA，而不是从离线原型直接外推。

## 七、三个容易被连续追问的示例

### 示例 A：用户说“查询张三工资并发给经理”

1. TaskProfile 识别工资查询和邮件发送两个子意图，以及“查询后发送”的依赖。
2. 如果经理邮箱缺失，返回 `CLARIFY`，不进入发送步骤。
3. Router 只在已授权且能力覆盖的 HR/Communication Agent 中选择。
4. 工资 Artifact 的读取经过所有权和敏感级别校验。
5. 发送属于外部副作用，工具前重新鉴权；若策略判为 `REVIEW_REQUIRED`，审批绑定这次任务、收件人和参数。
6. 明确 `DENY` 或 Artifact 校验失败时直接停止，不能用审批绕过。

### 示例 B：模型错误选择了高分但无权的 Agent

不会进入实际评分。权限过滤发生在评分前，无权 Agent 只进入 `excluded_agents`，记录 `PERMISSION_DENIED`；即使前层出现缺陷，派发 PEP 和工具 PEP 还会再次拒绝。这正是把安全从 Prompt 建议变成执行硬边界的意义。

### 示例 C：执行结束后返回了不该看的敏感数据

结果不会直接从 Agent 输出交给下游，而是形成带 owner、sensitivity 和 checksum 的 Artifact，经统一 Resolver 和 Guard 读取。跨用户未授权、敏感级别不符、文件缺失或 checksum 不一致都会失败关闭；审计只记元数据，不记敏感正文。当前还没有静态加密，因此不能把这种机制说成完整的数据安全方案。

## 八、答辩前建议修正或主动说明的口径

1. 第 2 页“行成执行闭环”应改为“形成执行闭环”。
2. 第 4 页的成功终态写 `ROUTE`，当前代码实际为 `DISPATCH`；口头说明二者语义相同，最好统一文字。
3. 第 4 页不要笼统说“授权、动作、范围、风险全部在 Router 硬过滤”。当前 Router 对无权、离线候选做硬过滤，对非复合任务再过滤动作和风险；范围仍是评分项，复合任务的逐子任务动作/风险硬过滤也未完全前移。
4. 第 5 页应主动说“33 条、规则模式、离线结构化评测”；不要让评委误以为是混合 LLM 的线上准确率。
5. 第 8 页 Fail Closed 的红条建议改成：“关键属性缺失、资源未知或校验失败 -> DENY/STOP；仅策略明确返回 REVIEW_REQUIRED 时进入审批。”
6. 不要把 SHA-256 说成防篡改、把 JSONL 说成不可篡改审计，也不要宣称已经实现真实身份认证、静态加密或生产部署安全。
7. 第 6、8 页的“数据范围”目前是架构目标和上下文字段，通用 scope containment 尚未在 PolicyEngine 中完整实现；现场应说明已硬执行的是角色/grant、敏感级别、所有权与受信共享等具体边界。

## 九、一句话术语表

- `TaskProfile`：主 Agent 对用户任务形成的结构化、可校验画像。
- `AgentCard`：Agent 的能力、契约和安全边界说明书。
- `RoutingDecision`：包含选中 Agent、Top-K、排除项、原因码和 trace 的路由证据。
- `S-ABAC`：加入任务场景的 Subject/Object/Scenario/Action 属性授权模型。
- `PDP`：集中作出策略决定的 Policy Decision Point，本项目对应 `PolicyEngine`。
- `PEP`：强制执行策略结果的 Policy Enforcement Point。
- `Artifact`：带所有者、来源、敏感度、校验和及血缘的步骤结果。
- `Fail Closed`：信息缺失或校验异常时默认拒绝，而不是默认放行。
