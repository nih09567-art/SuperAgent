面向数字员工复杂任务的多智能体协同与执行编排机制调研及原型成果报告
1 研究背景
随着大语言模型与智能体技术的发展，数字员工正在由传统固定流程自动化向具备任务理解、任务规划、工具调用和多智能体协作能力的智能任务执行系统演进。在人员查询、日程管理、课程检索、差旅办理、会议助手和消息发送等办公场景中，单轮问答或单工具调用相对容易实现，而复杂任务往往涉及多个步骤、多个业务角色及多个外部工具，需要进一步解决任务规划、多智能体协作、工具选择和执行恢复等问题。
本报告聚焦复杂任务执行编排相关工作，重点研究以下四个问题：
大语言模型生成的候选计划如何转化为可信、可执行的结构化计划；
多个 Agent 如何按照任务依赖关系协同，并可靠传递中间结果；
面对数量不断增加的 MCP Tool，如何缩小候选范围并降低工具误选风险；
长链任务发生暂停、中断或局部失败后，如何恢复执行并避免副作用重复发生。
围绕上述问题，首先对相关技术进行调研分析，在此基础上形成“可信计划—协同执行—工具选择—执行恢复”四部分技术路线，并在 SuperAgent 原型系统中完成相应机制的设计与验证。
2 调研分析
2.1 复杂任务规划与执行编排
复杂任务通常需要首先完成任务分解，再根据子任务之间的依赖关系组织执行。目前相关技术主要包括动态推理执行、显式计划生成和图结构工作流编排。
ReAct 将推理与行动交替进行，使模型能够依据工具或环境反馈持续调整下一步操作，具有较强动态适应能力，但完整执行路径通常在运行过程中逐步形成，不利于提前验证任务覆盖和执行边界。
Plan-and-Solve 采用“先规划、再执行”的方式，首先生成完整候选计划，再逐步完成子任务，能够降低复杂任务中的步骤遗漏问题。但计划本身仍由模型生成，无法直接保证其中涉及的 Agent、输入输出以及任务依赖与真实执行环境一致。
以 LangGraph 为代表的图结构工作流通过节点和边显式表示任务依赖关系，能够支持串行、并行、条件分支以及状态恢复，更适合具有明确业务流程的复杂任务。但当执行图来源于模型生成结果时，仍需要对图本身进行合法性验证。
基于以上分析，本原型采用“LLM 候选规划 + 确定性校验 + TaskGraph 执行”的方式。大语言模型主要负责开放式任务理解和候选计划生成，而系统通过结构化规则验证计划是否满足真实执行要求。
2.2 多智能体协作机制
复杂办公任务通常需要多个具有不同能力的 Agent 共同完成。现有多智能体系统主要包括对话式协作、图结构编排以及标准化 Agent 互操作等方式。
AutoGen 主要通过 Agent 间消息交互组织多角色协作，具有较高灵活性，适用于讨论、协商和开放式任务。但对于依赖关系明确的企业任务，仅通过消息传递容易将业务数据、执行状态和过程通信混合在一起。
LangGraph 通过图结构显式组织多个 Agent，可以明确描述并行执行、上下游依赖和多路汇合关系，更适合具有明确流程结构的复杂任务。
A2A 则更加关注独立 Agent 系统之间的标准化互操作，通过 Agent Card 描述能力，通过 Task 表示任务生命周期，并通过 Artifact 表达正式任务成果。其设计体现了“过程通信”和“正式结果交付”应当进行区分。
结合数字员工任务依赖较为明确的特点，本原型采用中心化 TaskGraph 编排，同时将执行控制和业务数据传递进行分离：
控制面：TaskGraph + Scheduler + StepResult
数据面：Artifact + ArtifactRef + ArtifactResolver
控制面负责管理“哪个任务在何时执行”，数据面负责管理“上游 Agent 的正式业务结果如何提供给下游 Agent”。
2.3 工具调用与 MCP 工具选择
随着 Agent 能够访问的工具不断增加，工具调用问题逐渐由“模型是否会调用工具”演变为“如何从大量工具中选择正确工具”。
Toolformer主要研究模型如何学习工具调用时机、工具类型和调用参数，重点解决模型自身的工具使用能力。
Gorilla进一步关注大量 API 环境中的调用错误和 API 幻觉问题，通过结合 API 文档检索缩小候选范围，提高工具调用可靠性。
ToolLLM面向更大规模的真实 API 集合，通过 API Retriever 先根据任务筛选相关接口，再由模型在候选集合中完成最终决策，体现了“大规模工具集合先检索、后选择”的技术思路。
MCP则主要解决 AI 应用与外部工具之间的标准化发现和调用问题。MCP Server 可以统一暴露工具名称、描述和 Input Schema，但在多个 MCP Server 同时提供大量工具后，如何进行候选筛选和最终选择仍需要由上层系统负责。
基于以上分析，本原型没有单独训练工具选择模型，而是利用 MCP Tool 元数据和业务上下文构建轻量级 Tool Resolver：
ToolRegistry → 确定性过滤 → 可解释评分 → Top-K → Tool / ABSTAIN
通过 Server、Scenario、Operation、Agent 和 Input Schema 等确定性条件先缩小候选范围，再进行排序；如果不存在合理候选，则返回 ABSTAIN，而不是强制选择工具。
2.4 长链任务恢复与执行韧性
复杂多 Agent 任务通常需要经历多个执行步骤，并可能调用远程 Agent 和外部业务系统。一旦发生服务异常、网络故障或用户暂停，如果从头重新执行全部步骤，不仅会增加执行成本，还可能导致邮件重复发送、日程重复创建等副作用。
LangGraph Persistence通过 Checkpoint 保存图执行状态，使系统能够记录已经完成的节点和已有输出，并支持中断恢复。
Temporal Durable Execution进一步强调将 Workflow 执行状态持久化，使工作流在进程或基础设施异常后能够继续执行，而不是重新开始整个流程。
对于具有外部副作用的任务，仅依赖 Checkpoint 仍不充分。例如外部操作已经完成，但本地成功状态尚未来得及持久化时发生异常，恢复后重新调用可能产生重复操作。因此还需要结合 Idempotency、Receipt 和 Reconciliation 等机制。
因此，本原型将“计算状态恢复”和“外部副作用安全”分别处理，使用 Checkpoint 保存 TaskGraph 已完成状态，并通过 Idempotency Key、Receipt 和 NEEDS_RECONCILIATION 控制写入和发送等副作用操作。
3 原型成果
3.1 候选计划可信化与 TaskGraph 构建
针对 Planner 输出存在不确定性的问题，本原型在规划层和执行层之间增加候选计划可信化过程：
用户任务
→ Planner 候选计划
→ 计划归一化
→ TaskProfile 覆盖校验
→ Agent Contract 校验
→ Schema 与数据依赖校验
→ TaskGraph
→ DAG 校验
→ Scheduler
Planner 主要负责产生候选步骤和数据依赖关系，但不能直接决定最终执行。系统结合可信 TaskProfile、Agent Contract 和 Schema 等结构化信息进行验证，Planner 不能自行扩展 Agent 能力边界，也不能构造系统中不存在的输入输出类型。
通过这一机制，将模型生成的开放式候选计划转化为系统能够校验和调度的 TaskGraph，使模型规划能力与确定性执行约束相结合。
3.2 基于 TaskGraph 与 Artifact 的多智能体协作
原型将多智能体执行划分为控制面和数据面。
控制面由：
TaskGraph → Scheduler → StepResult
构成。TaskGraph描述任务步骤和依赖关系，Scheduler根据已经完成的节点计算当前 READY 步骤，并负责并行执行、资源冲突控制、失败隔离和状态推进。
数据面由：
Agent → Artifact → ArtifactRef → ArtifactResolver → Agent
构成。Agent 成功执行后，其业务结果被转换为结构化 Artifact，并记录 ID、版本、生产 Agent、敏感级别、校验和及数据血缘等信息。下游步骤通过 ArtifactRef 引用正式业务结果，而不直接依赖上游 Agent 的内部运行状态。
因此，在当前设计中：
TaskGraph 描述执行依赖，Artifact 描述数据依赖。
两者通过 StepResult.outputs 建立关联，实现控制流与业务数据流的分离。
3.3 分层 MCP Tool Resolver
针对大量 MCP Tool 带来的候选膨胀问题，本原型实现分层工具选择机制：
ToolRegistry
→ MCP Server / Scenario 过滤
→ Operation 过滤
→ Agent 过滤
→ Input Schema 校验
→ 可解释评分
→ Top-K
→ Tool / ABSTAIN
系统首先利用业务场景和结构化约束排除明显不符合要求的工具，再根据工具名称、别名、意图、描述匹配和已知输入等信息进行排序，同时保留评分依据。

3.4 Checkpoint、安全暂停与恢复机制
针对长链任务中断和恢复问题，本原型设计了持久化任务控制机制，主要状态为：
RUNNING → PAUSE_REQUESTED → PAUSED → RUNNING
用户请求暂停后，系统不会立即终止当前正在执行的 Agent，而是记录 PAUSE_REQUESTED。Scheduler 等待当前并发批次执行完成，并完成关键 Artifact 和 Checkpoint 持久化后，在下一批步骤启动之前进入 PAUSED。
因此，当前采用的是Scheduler 安全点协作式暂停，而不是对远程 Agent 的即时强制终止。
Resume 时，系统根据 Checkpoint 中记录的 completed_steps、StepResult 和 ArtifactRef 恢复已有任务状态，已经成功完成的节点不重复执行。
关键结果提交顺序为：
保存 Artifact Payload
→ 保存 Checkpoint
→ 标记步骤完成
只有关键状态均成功持久化以后，步骤才被确认成功。
对于发送、写入等具有外部副作用的任务，系统进一步使用 Idempotency Key 和 Receipt。已经确认成功的操作不会在 Resume 后重复执行；如果外部操作结果无法可靠确认，则进入 NEEDS_RECONCILIATION，而不是直接重新调用。
自动重试和重新路由目前主要限制在只读步骤，对写入和发送等副作用操作采用更加保守的恢复策略。
3.5 综合案例验证
原型采用员工年假查询任务进行综合验证。
用户任务为：
“查询员工王强的在职状态、岗位和累计工龄，并依据年假相关规定判断其年假天数，最终生成 Markdown 汇总。”
系统根据任务结构动态形成：
HR Agent + Knowledge Agent
→ Report Agent
HR Agent 和 Knowledge Agent 可以并行执行，分别产生员工信息 Artifact 和政策信息 Artifact。当两路上游任务均完成后，Report Agent 通过 ArtifactRef 获取相关业务结果，并生成 Markdown 报告。
在进一步扩展的复杂任务中，还可以加入历史请假查询、报告生成、审批和模拟邮件发送，形成：
HR + Knowledge 并行
→ Office
→ Report
→ Approval
→ Email
其中，Report 汇总多路 Artifact，Email 仅在 Approval 通过后执行；审批拒绝时此前已经完成的业务成果仍然保留。
同时，通过幂等和 Receipt 机制保证重复 Approval 或 Resume 不产生第二次模拟发送。
通过上述案例，对动态 TaskGraph、多 Agent 并行与汇合、Artifact 数据传递、审批控制以及中断恢复等机制进行了综合验证。
4 总结
本阶段围绕数字员工复杂任务执行中的任务规划、多智能体协作、工具选择和执行恢复问题进行了相关技术调研，并结合实际原型完成了四方面机制设计。
在任务规划方面，采用“LLM 候选规划 + 确定性校验 + TaskGraph 执行”的方式，将模型规划能力与可信执行约束进行结合。
在多智能体协作方面，将执行过程划分为控制面和数据面，使用 TaskGraph、Scheduler 和 StepResult 管理任务执行关系，使用 Artifact、ArtifactRef 和 ArtifactResolver 管理 Agent 之间的结构化业务结果传递。
在工具选择方面，针对大量 MCP Tool 构建了基于 ToolRegistry、分层过滤、可解释评分、Top-K 和 ABSTAIN 的 Tool Resolver，用于降低候选空间和工具误选风险。
在任务恢复方面，结合 Checkpoint、安全点 Pause/Resume、Idempotency 和 Receipt，使长链任务能够在保存已有执行成果的基础上继续执行，并降低副作用重复发生的风险。
总体而言，本阶段工作的核心是：
将大语言模型产生的候选计划转化为一个可校验、可调度、可协作、可恢复的多智能体执行过程。
当前系统仍属于研究原型。MCP Tool Resolver 主要运行于 audit 模式；暂停机制属于 Scheduler 安全点协作式暂停，而非远程 Agent 的即时抢占；正式身份认证、生产级密钥管理、静态加密和公网生产部署等能力也不属于当前研究范围。
后续可进一步围绕 Tool Resolver 强制执行、运行时动态任务调整、副作用对账机制，以及更大规模 Agent 和 MCP Tool 环境下的稳定性与泛化能力开展研究。
